2. Descripción General
 
2.1 Perspectiva del producto
 
 
El módulo de "Confirmación de Pedido y Pago Seguro" opera como un 
subsistema independiente pero altamente integrado dentro de la 
plataforma web principal de la Maderería.
 

 
Visión Externa y Contexto Operacional:
 
El sistema actúa 
como el puente crítico entre la selección del cliente y la 
consolidación de la venta. Se comunica de forma externa 
con una pasarela de pagos para procesar la transacción 
económica.
 

 
Relación con otros sistemas:
 
Una vez que el pago es 
aprobado, el módulo interactúa unidireccionalmente con los 
sistemas de Almacén y Envíos, limitándose a enviar 
notificaciones de actualización de estado para descontar el 
inventario y programar la ruta, sin gestionar la lógica intern
a 
de dichos departamentos.
 

 
UX \(Experiencia de Usuario\
 
La interfaz está diseñada 
para minimizar la fricción cognitiva durante el proceso de 
pago, aislando los complejos procesos criptográficos \(como 
la firma del contrato\en el backend, presentando al usuario 
únicamente indicadores visuales de confianza y seg
uridad.

Descripción del Diseño de Software \(SDD\
 
1. Introducción al Diseño
 
1.1 Propósito y alcance del diseño
 
El propósito de este diseño es traducir los requisitos de la Especificación 
de Requisitos de Software \(ERS\en una solución web sencilla, ejecutable 
 
14
 
en localhost y suficientemente clara para demostrar principios de 
ciberseguridad. El diseño cubre el recorrido completo de la compraventa 
de madera: inicio de sesión, consulta y personalización del producto, 
carrito, checkout, generación del contrato, pago
 
en un entorno de pruebas 
y confirmación del pedido.
 
El backend será responsable de la lógica de negocio, la validación de 
datos, el control de acceso, el registro de auditoría y la comunicación con 
el proveedor de pagos. El frontend permitirá al cliente interactuar con el 
catálogo y consultar el estado de s
u pedido. La logística física, la gestión 
avanzada del almacén y el envío real quedan fuera del sistema; después 
de una transacción aprobada sólo se enviará una notificación de cambio 
de estado al área correspondiente.
 
2. Descripción de la Arquitectura
 
2.2 Vista Lógica
 
La vista lógica organiza las responsabilidades del software y evita que la 
interfaz tome decisiones que corresponden al servidor. El navegador 
consume endpoints JSON; los controladores reciben las solicitudes y 
comprueban la sesión; los servicios ejecutan 
las reglas de negocio; y la 
capa de datos consulta o actualiza las entidades mediante 
transacciones.
 
Capa de presentación: 
componentes de login, catálogo, detalle de 
producto, carrito, checkout, confirmación y panel de consulta para el 
administrador o contador.
 
Capa de aplicación: 
controladores para autenticación, productos, 
carrito, pedidos, contratos, pagos y auditoría. Cada controlador valida el 
rol y delega la operación al servicio correspondiente.
 
Capa de dominio: 
reglas para comprobar stock, calcular el importe a 
partir de datos confiables del servidor, crear la orden, generar el 
contrato y cambiar el estado del pedido solo cuando se cumplan las 
condiciones definidas.
 
 
15
 
Capa de infraestructura: 
ORM o repositorios, SQLite, almacenamiento 
local de claves de demostración, cliente HTTPS de la pasarela y 
generador de logs.
 
La comunicación entre capas se hará mediante objetos o esquemas 
validados. El frontend podrá solicitar una operación, pero no podrá 
asignar por sí mismo un precio, aprobar un pago, cambiar el stock ni 
consultar bitácoras de otro usuario.

El flujo normal inicia con la autenticación del cliente y termina con la 
confirmación del pedido. En cada paso el backend valida la sesión y 
conserva el estado en la base de datos. Si el inventario es insuficiente, 
el usuario regresa al catálogo o modifica
 
el carrito. Si el proveedor 
rechaza el pago o no responde, la orden queda pendiente o rechazada 
y el cliente recibe un mensaje general que no expone información 
sensible.

2.4 Vista de Despliegue
 
Durante la demostración, todos los componentes principales se 
ejecutarán en una sola laptop. El navegador accederá al frontend 
mediante localhost; el servidor FastAPI atenderá la API; y SQLite 
almacenará los datos en un archivo local. La pasarela de pagos 
será el 
único componente fuera de la laptop y se utilizará exclusivamente en 
modo Sandbox.
 
Ejecución local: 
un proceso para el backend y el servidor de archivos 
estáticos del frontend. La base de datos y los logs se guardarán en el 
directorio del proyecto con permisos restringidos al usuario de la laptop.
 
Comunicaciones: 
para una demostración básica se puede usar HTTP 
en localhost; cuando se prueben credenciales o una integración externa 
se habilitará HTTPS con un certificado local de desarrollo. En ningún 
caso se enviarán secretos por una conexión sin protección hacia el 
tercero.
 
Configuración: 
las claves de prueba, la cadena de conexión y los 
secretos de sesión se leerán desde variables de entorno o un archivo 
local excluido del control de versiones. No se incluirán secretos dentro 
del código fuente.
 
Límite del despliegue: 
Docker, un servicio cloud y un balanceador no 
son necesarios para este prototipo. Podrían incorporarse después si el 
proyecto se quiere escalar.

id, correo, password_hash, rol, estado y fecha de alta. 
Nunca se almacenará la contraseña en texto plano.
 

 
Sesiones: 
id, usuario, hash del token de sesión, fecha de

cookie del navegador.
 

 
Productos: 
id, tipo de madera, marca, color, textura,

Carritos y partidas: 
carrito, producto, características 
seleccionadas y cantidad. Un usuario podrá tener un carrito activo 
y el backend recalculará el total.
 

 
Pedidos y partidas: 
orden, usuario, estado, total, fechas e 
identificador de idempotencia; las partidas conservarán el precio 
aplicado y la configuración solicitada.
 

 
Pagos y contratos: 
identificador del proveedor, estado de la

pública y fecha de generación. No se guardarán datos bancarios.

Acciones críticas:

3.3.2 Diseño del backend y de las APIs
 
Las interfaces se expondrán como endpoints REST que intercambian 
JSON. Los esquemas de entrada y salida se validarán en el servidor y 
cada respuesta utilizará un código HTTP coherente. Como referencia, el 
contrato mínimo de la API es el siguiente:
 
POST /api/auth/login y POST /api/auth/logout: 
inician o terminan la 
sesión y devuelven únicamente el estado de autenticación, nunca la 
contraseña ni el hash.
 
GET /api/productos y POST /api/carrito/items: 
consultan el catálogo y 
agregan una configuración al carrito después de validar el producto y la 
cantidad.
 
GET /api/carrito y POST /api/pedidos/preparar: 
muestran el resumen 
y vuelven a calcular precio, stock e importe antes de generar la orden.
 
POST /api/contratos/{id}/firmar: 
genera el documento canónico, su 
hash y la firma digital de demostración asociada al usuario autenticado.
 
POST /api/pagos y POST /api/pagos/webhook: 
crean la operación en 
el sandbox y reciben la confirmación firmada o verificada por el 
backend. Se usará una clave de idempotencia para no duplicar cargos.
 
GET /api/pedidos/{id} y GET /api/auditoria: 
permiten consultar el 
resultado propio del cliente o la información de auditoría al rol interno 
autorizado.
